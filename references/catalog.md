# 측정 항목 카탈로그: 1단계

`techniques.md` 의 기법을 가르기 위한 질문 8개. **기법 목록이 바뀌면 이 목록도 다시 뽑는다.**
어떤 기법도 가리키지 않는 질문은 뺀다.

각 항목은 `측정 → 결과 → 결정` 세 줄로 쓴다. 결정이 안 나오면 넣지 않는다.

## 측정 항목은 어디서 나오는가

한 번에 다 나오지 않는다. 항목 설계를 한 덩어리로 하면 놓친다.
그리고 **첫 바퀴와 그다음 바퀴는 항목이 나오는 자리가 다르다.**

### 첫 바퀴 · 아직 아무것도 안 쟀을 때

```
1a  사전 지식        데이터를 열기 전에 아는 것 → 가설 → 항목
1b  대표 파일 정독    직접 읽는다 → 예상 못 한 표기·예외 발견
1c  예상 밖 값 탐지   queries/outliers.sql 이 8종을 신고
```

**1a 없이 1b 부터 하면** 길이 분포 확인 수준에 머문다.
**1a 만 하고 1b·1c 를 건너뛰면** 사전 지식이 빗나간 걸 못 잡는다.
실제 사례에서 항목이 **1차 31개 → 2차 18개**로 늘었고, 사전 지식 2건이 실측에 뒤집혔다.

### 그다음 바퀴 · 재고 나서야 생기는 자리

여기가 비면 루프가 사람을 기다린다. **다음에 뭘 잴지를 사람이 정해주게 되고, 그 순간 루프가 멈춘다.**
아래 네 자리는 전부 **1바퀴에는 존재하지 않다가 측정 결과가 만들어낸 것**이다.
바퀴가 끝나면 이 넷을 훑어 `next_measure` 를 채운다. 넷 다 비면 그 축이 닫힌 것이다.

```
2a  값이 갈린 자리      같은 지표에 값이 둘 이상이면, 그 값을 만든 코드를 각각 읽는다
2b  규칙이 만든 새 분포   재적용 결과는 원본 기준으로 내린 판정을 무효로 만든다
2c  안 닫힌 회계        분해가 남으면 그 잔차가 다음 항목이다. 단 크기부터 본다
2d  검사기가 뱉은 후보   validate.py · ledger.py check · outliers.sql 의 신고
```

**2a · 값이 갈린 자리.** 대개 다른 것을 센 것이지 하나가 틀린 게 아니다.
실제 사례에서 청크 수가 `198,217` 과 `235,296` 으로 갈렸는데, 원인은 상한 해석이었다.
한쪽은 1,800을 **분할 판단 경계**로 두고 상한을 8,000으로 잡았고, 다른 쪽은 1,800을 **상한**으로 읽었다.
분모도 갈려 있었다(폐지 스텁 47파일 포함 여부 · 삭제 조문 정의 · 청크 문자에 prefix 포함 여부).
**두 값을 나란히 적고 넘어가면 이게 안 보인다.** 값을 만든 코드를 읽어야 나온다.

**2b · 규칙이 만든 새 분포.** 6단계 재적용은 원본에 없던 분포를 만든다. 그 분포는 앞서 내린 판정을 흔든다.
실제 사례에서 50자 미만 조각이 `조 단위 7,555 → 항·호 14,763 → 문단·슬라이딩 15,458` 로 늘었다.
1바퀴는 **조 단위 원본**을 읽고 "짧아도 완결된 규범"이라 판정했는데, 층을 갈라 다시 보니
그 판정은 조 층(47.2%)에만 성립하고 나머지 52.8%는 자립하지 않았다.
**규칙을 적용했으면 그 규칙이 건드린 판정을 전부 다시 센다.**

**2c · 안 닫힌 회계.** 분해가 남으면 남은 몫이 항목이다.
실제 사례에서 못 담은 문자를 가르니 1,889,141이 설명되지 않았고, 조 헤딩을 근사가 아닌 실측으로
바꾸고 상위 헤딩 498,652자를 넣으니 801,330으로 줄었다.
**단 크기부터 본다.** 801,330은 원본의 0.63%라 어떤 설계도 못 바꾼다. 거기서 닫는 게 맞다.
`그 값이 설계를 바꾸는가` 는 첫 바퀴만의 기준이 아니다.

**2d · 검사기가 뱉은 후보.** 사람이 안 봐도 신고된다. 판정이 아니라 후보이므로 하나씩 원자료로 확인한다.
`validate.py` 의 문서 간 불일치, `ledger.py check` 의 현행 충돌·분모 누락, `outliers.sql` 의 예상 밖 값.

### 1a · 사전 조사

데이터를 열기 전에 도메인 문헌·표준으로 알아낸다.

- 이 도메인의 문서는 어떤 **위계**를 갖는가 (묶음 → 단위 → 하위 단위)
- 어떤 **부속물**이 붙는가 (부록·별표·이력·주석)
- 무엇이 **무효·폐기**를 뜻하는가
- 문서끼리 어떻게 **참조**하는가
- 어떤 **메타**가 표준으로 붙는가

여기서 나온 가설이 1차 측정 항목이 된다.

### 1b · 대표 파일 선정

아무거나 고르면 안 된다. **구조 요소를 가장 많이 가진 파일**을 고른다.
`survey.py` 가 구조 마커 후보를 뽑고 그 요소를 가장 많이 포함한 파일을 추천한다. **3~5건이면 충분하다.**

실제 사례: `같은 계열 문서가 함께 있을 것` → 948곳 → 그중 8개 구조 요소를 하나도 빠뜨리지 않은 1건.

### 1c · 예상 밖 값 탐지

전수를 정독할 수는 없다. 스크립트가 신고하게 한다. `queries/outliers.sql` 이 이 8종을 돈다.

| 블록 | 탐지 | 실제 사례 |
|---|---|---|
| `[1]` | 파싱 · 인코딩 · 적재 실패 | 버리지 말고 카운트한다. 그 자체가 측정 결과다 |
| `[2]` | 분포의 위쪽 꼬리 | 최대 866,894자 문서. 청킹 상한과 컨텍스트 모델이 여기서 갈린다 |
| `[3]` | 분포의 아래쪽 꼬리 | 가장 짧은 쪽에 스텁 · 플레이스홀더가 숨는다 |
| `[4]` | 빈 문서 | 10자 미만. 있으면 적재 범위(Q5)에서 뺄 후보다 |
| `[5]` | 메타 키별 값 분포 | 문서 종류 38종(사전 지식은 5~6종뿐) · 반대로 `상태`·`법령분야`는 한 값이 100% → 필터 불가 |
| `[6]` | 메타 키 결측 | 그 키를 가진 문서 비율. 분모는 `doc` 전체다 |
| `[7]` | **코퍼스가 아닌 파일** | `README.md` 1건이 섞여 분모가 124,357 vs 124,356 으로 갈렸다 |
| `[8]` | **마커 표기 변종** | `【이 유】`·`【이  유】`·`【이유】` 3종 **124,509건** · `【피고,상고인】` **11종** |

**마커 변종이 가장 위험하다.** 한 형태로 정규식을 쓰면 나머지를 통째로 놓치고
측정이 조용히 틀린다. 실측하기 전에 `outliers.sql` 로 변종부터 확인한다.

## 전수 스캔을 줄인다

측정 항목이 늘 때마다 새 정규식을 `body` 전체에 걸면 항목 수만큼 전수 스캔이 쌓인다.
**한 번에 뽑아 작은 테이블로 두고, 이후 질문은 그걸 읽는다.**

| 테이블 | 만드는 법 | 무엇에 쓰나 | 실측 |
|---|---|---|---|
| `tok` | `index.py` | 줄머리 마커 질문 전부 | 원문 문자의 **7~28%** (법령 27.5% · 판례 7.2%) |
| `tok_skel` | 자동 (뷰) | 골격별 출현율. 새 측정 설계의 출발점 | 골격은 26자로 자른다 |
| `tok_variant` | 자동 (뷰) | 공백만 다른 표기 변종 | · |
| `meta` | `index.py` | frontmatter 키/값 질문 · 메타 필터 성립 여부 | · |
| 파생 단위 | 측정 SQL (`--write`) | 조각별 특징을 한 번에 뽑아 컬럼으로 | 이후 질문 비용 0 |

**이득의 정체**: `tok` 은 원문의 극히 일부가 아니다. 코퍼스에 따라 원문 문자의 7~28%를 차지한다.
그래도 이득이 있는 이유는 둘이다. **스캔 대상이 1/4 이하로 줄고**, 각 행이 50자 이하라
**정규식이 긴 문서 본문이 아니라 짧은 문자열에만 걸린다.** 항목이 30개면 이 차이가 30번 쌓인다.

**경계 1 · 줄머리만 담는다.** `tok` 은 마커 접두 + 39자 이내를 담는다(실측 최대: 법령 45자 · 판례 50자).
문장 중간의 표현은 없다.
`"제N조 헤딩이 몇 개"` 는 `tok` 이 정확하지만, `"본문에 별표가 몇 번"` 은 `doc` 을 봐야 한다.
`tok` 을 쓰면 줄머리에 걸린 것만 세어 **조용히 적게 나온다.**

**경계 2 · `skel` 은 26자로 잘린다.** 골격 비교는 앞 26자만 본다(`substr(...,1,26)`).
**26자 이후가 다른 마커는 같은 골격으로 묶인다.** 긴 마커를 가르려면 `tok.raw` 를 본다.

**파생 단위를 만들 때는 특징을 한 번에 다 뽑는다.** 조각을 만들면서 길이·항 수·호 수·개정 표시·
인용 수를 같이 컬럼으로 넣어두면, 나중에 "호가 10개 넘는 조각은?" 같은 질문이 스캔 없이 끝난다.
나중에 하나씩 물으면 그때마다 전수 스캔이다.

**줄 단위로 쪼개지 않는다.** `str_split(body, '\n')` 은 1.3억 자를 400만 개 문자열 원소로 흩어
메모리에 올린다. 통째로 정규식 한 패스면 원소 생성 없이 같은 결과를 낸다.

**파생 단위 생성은 팀이 동시에 못 돈다.** `--write` 가 DB 락을 잡으므로 단독으로 먼저 돌리고,
그 표를 읽는 측정들을 그다음에 병렬로 흘린다(`orchestration.md` 의 동시성 함정).

## 질문 8개

### Q1. 문서를 자르는 구조 마커가 일관된가

**정하는 것**: 구조 기반 청킹 채택 여부 (기법 A)
**정본**: `queries/markers.sql`. `index.py` 가 만든 `tok` · `tok_skel` · `tok_variant` 를 읽어
마커 출현율 · 골격별 분포 · 표기 변종을 한 번에 낸다. 아래는 감을 잡기 위한 축약형이다.

```sql
-- 마커 후보별 출현 파일 비율. survey.py 가 뽑은 후보를 넣는다
SELECT
  count(*) FILTER (WHERE regexp_matches(body, '(?m)^#+ *제[0-9]+조')) AS has_marker,
  count(*) AS total
FROM doc;
```

**판정**: 파일의 대다수가 마커를 가지면 구조 기반 청킹. 아니면 재귀 분할.
**함께 볼 것**: 마커의 **깊이 사용률**. 사전 지식이 5단이어도 실제로는 1단만 쓸 수 있다
(실제 사례: 파일의 64.3%가 최소 단위만 사용 → 5단 파서 폐기).

### Q2. 그 단위의 길이 분포

**정하는 것**: 분할 임계값 · 임베딩 모델 컨텍스트 · ANN 필요 여부 (기법 A · D)
**정본**: `queries/basics.sql` 의 길이 분포 · 구간별 분포 블록.

```sql
SELECT quantile_cont(n, [0.5, 0.95, 0.99]) AS q, max(n) AS mx, count(*) AS n_unit
FROM unit;
```

**판정**: p99 와 max 를 본다. **평균과 중앙값만 보면 틀린다.**

**함정 1**: "긴 조각을 어떻게 쪼개나"가 과제일 것 같지만 실측하면 아닐 수 있다.
실제 사례에서 8K 초과가 68건(0.04%)뿐이었고, 진짜 과제는 **50자 미만 7,555건(3.92%)** 이었다.

**함정 2**: 여기서 잰 것은 **원본 단위**의 분포다. 분할하면 짧은 쪽이 늘어나므로
이 값으로 내린 판정을 분할 후 조각에 그대로 쓸 수 없다. 같은 사례에서 50자 미만이
`조 단위 7,555 → 항·호까지 14,763 → 문단·슬라이딩까지 15,458` 로 **두 배가 됐다.**
쪼갤수록 는다. 길이 하한이나 자립성 판정은 **6단계 재적용 뒤에 다시** 본다.

### Q3. 조각 하나가 단독으로 답변 근거가 되는가

**정하는 것**: 부모 문서 동반 조회 · 요약 생성 (기법 B)

**수치로 안 된다.** 층화 표본을 직접 읽는다 → `llm-judgment.md`
**빈도만 보고 정하면 틀린다.** 실제 사례에서 50자 미만 조각 7,555건은
버릴 대상이 아니라 법적으로 완결된 규범이었다.

### Q4. 조각 앞에 붙일 맥락이 원문에 있는가

**정하는 것**: prefix 부착 vs 문맥 부착 검색 (기법 B)
**정본**: `queries/markers.sql`. Q1 과 같은 파일이다. 마커가 **있는가**(Q1)와
그 마커가 조각 **위에 붙어 있는가**(Q4)는 같은 `tok` 테이블에서 갈린다.

```sql
-- 상위 구조 마커가 조각 위에 실제로 존재하는 비율
SELECT count(*) FILTER (WHERE regexp_matches(body, '<상위 마커>')) * 100.0 / count(*) FROM doc;
```

**판정**: 있으면 문자열로 붙인다(공짜). 없으면 LLM 생성을 검토한다(비쌈).

### Q5. 무엇을 적재에서 빼는가

**정하는 것**: 임베딩 비용과 오답 소스 (기법 C)

무효·이력·첨부 위임·저가치 구간을 분류해 **문자 수로** 잰다.
**비용은 문자 수에 걸려 있으므로 건수가 아니라 분량으로 센다.**

실제 사례: 534M자 중 241M자(45.1%)가 요약도 인용도 없는 구간 → 코퍼스 전체가 임베딩에서 빠졌다.

### Q6. 메타로 거를 수 있는가

**정하는 것**: 메타 필터 성립 여부 (기법 G)

`meta` 는 `index.py` 가 만드는 `meta(doc_id, key, val)` 뷰다. `doc.fm_raw` 에 통째로 들어 있는
frontmatter 를 키/값 행으로 편 것이다. `doc` 에는 `key`·`val` 컬럼이 없으므로 이 뷰를 거친다.

```sql
-- 값 분포와 결측률. 한 값이 100% 면 필터가 아니다
-- 함정: meta 에는 그 키를 가진 문서만 행으로 있다. 결측을 meta 안에서 세면 언제나 0% 다.
--       보유율의 분모는 반드시 doc 전체(load_ok)로 잡는다
WITH total AS (SELECT count(*) AS n FROM doc WHERE load_ok)
SELECT key,
       count(DISTINCT val)                   AS n_val,
       round(max(cnt) * 100.0 / count(*), 1) AS top_pct,   -- 최빈값 점유율
       round(count(DISTINCT doc_id) * 100.0 / (SELECT n FROM total), 1) AS have_pct
FROM (SELECT doc_id, key, val, count(*) OVER (PARTITION BY key, val) AS cnt FROM meta)
GROUP BY key ORDER BY n_val, have_pct DESC;
```

**판정**: `n_val = 1` 이면 필터가 아니다. `top_pct` 가 95 이상이어도 사실상 아니다.
`have_pct` 가 낮으면 그 필터는 코퍼스 일부에만 걸리므로 나머지의 처리를 함께 정해야 한다.

### Q7. 코퍼스가 둘 이상이면 어떻게 연결되는가

**정하는 것**: 교차 검색 · GraphRAG · 임베딩 대상 축소 (기법 H)
**정본**: `queries/crosslink.sql`.

**정규식으로 참조 문자열을 뽑는 것까지는 측정이 아니다.** 뽑힌 문자열은 링크의 **후보**일 뿐이고,
그 후보가 상대 코퍼스에 실제로 있는지는 아직 모른다. 문서에 이름이 적혔다는 사실과
그 이름의 문서가 검색 대상에 있다는 사실은 다르다. 이 둘을 구분하지 않으면
연결률이 부풀고, 그 부푼 값 위에서 교차 검색을 채택하게 된다.

그래서 `crosslink.sql` 은 두 단계로 잰다. 상대 코퍼스에서 **실재하는 이름 목록**을 먼저 만들고,
추출한 참조 문자열을 그 목록에 대조해 **실재하는 것만 링크로 인정**한다.
분모는 참조 건수가 아니라 대조를 거친 건수다.

**여기는 1차 측정으로 끝나지 않는다.** 반드시 `hypothesis-validation.md` 로 넘긴다.
이번 사례에서 가장 큰 결정이 여기서 나왔다. 판례 코퍼스 원문 586,670,534자 전체가
임베딩 대상에서 빠졌고, 근거는 1차 측정이 아니라 그 뒤의 교차검증이었다.

### Q8. 중복 · 버전이 있는가

**정하는 것**: 대표 선택 규칙 (기법 C)
**정본**: `queries/basics.sql` 의 형제 파일 · 파일 조합 · 동명 파일 블록.

```sql
SELECT norm_key, count(*) n FROM doc GROUP BY 1 HAVING n > 1 ORDER BY n DESC;
```

**한 조건으로 부족하다.** 실제 사례에서 "폐지 스텁 아님" 하나로 고르니
1940년대 구법으로 이동했다. **비스텁 → 최신 → 분량** 3단 정렬이 됐다.
